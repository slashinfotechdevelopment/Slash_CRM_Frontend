### Global API Guidelines
1. **Base URL:** `http://localhost:5000` (stored in `.env` as `VITE_API_BASE_URL`). All endpoints specify `/api/...`.
2. **IDs in URLs:** Always use the record CUID (e.g. `cmw4w1uxb00038suz1cspz6oc`), never display codes like `TASK001` or `LEAD-001`.
3. **HTTP Client:** Exactly ONE HTTP client instance handles auth header injection, synchronized token refresh queue, timeout, and friendly error translation.
4. **Super Admin Guard:** System roles (`SUPER_ADMIN`, `ADMIN`) are protected against accidental deletion or privilege stripping.

## Post-Regression Invariants & DTO Alignments

1. **Lead Update (`PUT /api/leads/:id`):** [Verified in backend DTO]
   - Backend applies `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })`.
   - Sending database/audit fields (`id`, `leadCode`, `createdAt`, `updatedAt`, `assignedTo`, `pipelineStage`, etc.) triggers HTTP 400 rejection `["property id should not exist", ...]`.
   - Frontend `handleEditSubmit` now constructs a strict whitelist matching `UpdateLeadDto`: `leadName`, `phone`, `email`, `companyName`, `estimatedValue`, `priority`, `requirementDescription`.

2. **Lead Follow-Up (`POST /api/leads/:id/follow-ups`):** [Verified in backend DTO]
   - `scheduledAt` is decorated with `@IsDateString()`.
   - HTML5 `<input type="datetime-local">` outputs `YYYY-MM-DDTHH:mm`. It must be converted via `new Date(val).toISOString()` before submission.

3. **Leave Type Status & Versioning (`/api/leave/types`):** [Verified in backend DTO]
   - `LeaveType.status` is `RecordStatus ('ACTIVE' | 'INACTIVE')`, not boolean `isActive`.
   - `UpdateLeaveTypeDto` accepts `status?: RecordStatus`. Outgoing payloads in `leave.connector.ts` map boolean `isActive` to `status: 'ACTIVE' | 'INACTIVE'` and strip `isActive`.
   - `LeaveType.policies` returns policy versions where version index is `version: Int` (not `versionNumber`).
   - Active policy version is resolved as `policies.find(p => !p.effectiveTo) || policies[0]`.

4. **Employee Leave Balances (`GET /api/leave/balances`):** [Verified in backend DTO]
   - When called without `userId`, the endpoint returns a flattened summary roster:
     `{ userId, userName, userCode, departments: string[], leaveTypeId, leaveTypeName, leaveTypeCode, year, allocatedDays, carriedForward, adjustedDays, usedDays, pendingDays, availableDays }`.
   - Frontend `LeaveBalancesPage` directly consumes these flattened fields with zero fallbacks to undefined nested models.
